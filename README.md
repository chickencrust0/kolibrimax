# chess-school-bot (MAX + impulseCRM)

Бот для чат-платформы MAX, интегрированный с impulseCRM. Портирован с
исходного бота на Telegram/aiogram + AlfaCRM — та же функциональность
(вход по телефону, расписание, ДЗ, баланс, заявки на перенос, рассылки,
сводки, напоминания), другой мессенджер и другая CRM.


## Что умеет бот

**Новый посетитель (лиды).** `/start` от незнакомого человека запускает
воронку: возраст детей → подходящие направления → телефон. Заявка уходит
менеджеру. Каталог направлений и возрастные рамки — в `bot/directions.py`.

**Родитель.** Расписание, домашние задания, баланс абонемента, заявка на
перенос, обращение к менеджеру.

**Преподаватель.** Своё расписание; в карточке занятия у каждого ученика
две кнопки — «пришёл» (пишется в CRM через `check_visits/check`) и «не
пришёл» (копится в БД бота). Плюс ДЗ, отчёт, заявка на перенос.

**Менеджер.** Рассылки, заявки на перенос, сводка за период, обращения
поддержки и неявки: в 21:00 приходит сводка, по каждой неявке кнопки
«🔥 занятие сгорело» (списание через `burn_one`) и «🙏 уважительная».

## Быстрый старт

```bash
pip install -r requirements.txt
cp .env.example .env
# заполните .env — см. разделы ниже
python main.py
```

## 1. Настройка MAX

1. Зарегистрируйте бота через `@MasterBot` (или аналог) в MAX, получите токен.
2. `MAX_BOT_TOKEN=<токен>` в `.env`.
3. `MAX_MODE=polling` — для старта ничего больше не требуется. Для
   продакшена переключитесь на `MAX_MODE=webhook` (нужен публичный
   HTTPS с доверенным сертификатом, в т.ч. Минцифры — самоподписанные
   сертификаты и HTTP с 25 мая 2026 не поддерживаются, см.
   dev.max.ru/docs-api) и заполните `MAX_WEBHOOK_URL`.
4. `ADMIN_MAX_IDS` — ID пользователей-менеджеров через запятую. Узнать
   свой ID можно, написав боту `/start` и посмотрев лог первого входа
   (там будет виден `from_user.id`), либо через сервисы вида
   `@myid_bot`, если такой есть в MAX.

### Важное архитектурное отличие от Telegram-версии

В MAX нет постоянной reply-клавиатуры (панели кнопок под полем ввода) —
только inline-клавиатуры, прикреплённые к конкретному сообщению (см.
dev.max.ru/docs-api, раздел «Клавиатура для чат-бота»). Поэтому меню
ролей (расписание/ДЗ/баланс/рассылка и т.д.) реализованы как
inline-кнопки в сообщении меню, а не как постоянная панель:

* после входа /start бот присылает сообщение с меню — кнопки в нём
  рабочие сколько угодно долго, даже если сообщение прокрутилось вверх
  по истории чата;
* если нужно вызвать меню заново — достаточно снова отправить `/start`
  (или просто открыть диалог с ботом — сработает событие `bot_started`).

## 2. Настройка impulseCRM

1. В интерфейсе CRM: иконка профиля → «Настройка API» → «Обновить ключ».
2. Кнопка «Пример запроса» покажет ваш домен и точный префикс пути —
   скопируйте их в `.env`:
   ```
   IMPULSE_DOMAIN=https://ваш-домен.impulsecrm.ru
   IMPULSE_LOGIN=...
   IMPULSE_API_KEY=...
   IMPULSE_API_PATH=/то-что-показал-пример-запроса/{entity}/{action}
   ```
3. **Обязательно** запустите скрипт снятия схемы перед боевым запуском.

   macOS/Linux (bash):
   ```bash
   export IMPULSE_BASE="https://ваш-домен.impulsecrm.ru"
   export IMPULSE_USER="логин"
   export IMPULSE_KEY="ваш-ключ"
   export IMPULSE_API_PATH="/api/public/{entity}/{action}"
   python impulse_introspect.py --md schema.md --json schema.json
   ```

   Windows (PowerShell — так выглядит `python main.py` в ваших логах,
   значит нужен именно этот вариант, `export` в PowerShell не работает):
   ```powershell
   $env:IMPULSE_BASE="https://ваш-домен.impulsecrm.ru"
   $env:IMPULSE_USER="логин"
   $env:IMPULSE_KEY="ваш-ключ"
   $env:IMPULSE_API_PATH="/api/public/{entity}/{action}"
   python impulse_introspect.py --md schema.md --json schema.json
   ```
   `$env:` действует только в текущем окне PowerShell — при следующем
   запуске выполните все команды заново (или объедините в один блок).

   Он заберёт по одной записи из каждой из 25 сущностей и покажет
   реальные имена полей. Сверьте `schema.md` с константами
   `IMPULSE_FIELD_*` в `.env` (см. следующий раздел) и поправьте
   несовпадающие имена — без правки кода.

### Что подтверждено документацией impulseCRM, а что нет

Справочник по API impulseCRM, на основе которого сделан клиент, честно
помечает несколько пробелов (раздел 10 справочника — «tech.impulsecrm.ru
запрещает автоматический доступ, поэтому интерактивная документация в
него не попала»). Это отражено в `impulse_client.py` и `settings.py`
как настраиваемые константы, а не зашито намертво:

| Что | Статус | Где настраивается |
|---|---|---|
| Авторизация: `Authorization: Basic <ключ>` БЕЗ доп. base64 | **Подтверждено** реальным примером из личного кабинета | `impulse_client.py`, `IMPULSE_API_KEY` |
| Префикс пути API (`/api/public/{entity}/{action}`) | **Подтверждено** тем же примером | `IMPULSE_API_PATH` |
| `page` с 1, `sort`={"поле":"asc/desc"}, `columns` для точного/диапазонного фильтра | **Подтверждено** тем же примером | `impulse_client.list_()` |
| Даты в `columns` — Unix-timestamp в секундах | **Подтверждено** (для поля `created`) | `_to_datetime_str()` понимает и timestamp, и строку |
| ФИО клиента — 3 camelCase-поля (lastName/name/middleName) | **Подтверждено** тем же примером | `IMPULSE_FIELD_CLIENT_*`, `extract_user_name()` |
| Состав полей schedule/reservation/*_account (только client был в примере) | Не публикуется | `IMPULSE_FIELD_*` в `.env`, сверить `impulse_introspect.py` |
| Обёртка ответа list (items/total/…) | Не публикуется | `_extract_items()` перебирает несколько вариантов |
| `update`: частичный или полный | Не публикуется | клиент всегда отправляет полную модель записи |
| Статусы занятия (число vs булевы флаги) | Не публикуется | `STATUS_PLANNED/CANCELLED/CONDUCTED` в `.env` |
| Лимит запросов/сек | Не публикуется | `IMPULSE_RPS=3.0` (консервативно) |

Если что-то не работает после первого запуска — почти наверняка дело
в одной из этих строк. Технической поддержке impulseCRM можно задать
эти же вопросы напрямую: Telegram `@impulsCRM_manager`.

### Баланс/абонемент

impulseCRM хранит остаток занятий не на карточке `client`, а в отдельной
сущности абонемента. По умолчанию используется `individual_account`
(`IMPULSE_ACCOUNT_ENTITY`) — поменяйте на `group_account`, если у вас
преимущественно групповые занятия, либо агрегируйте оба (потребует
доработки `impulse_client.get_balances_map`).

## 3. Диагностика проблем при первом запуске

### `CERTIFICATE_VERIFY_FAILED` / `unable to get local issuer certificate` при обращении к MAX

`platform-api2.max.ru` подписан сертификатом **НУЦ Минцифры России**
(Russian Trusted Root CA) — сама документация MAX прямо предупреждает
об этом: «убедитесь, что добавили сертификат Минцифры в список
доверенных». Обычные бандлы вроде `certifi` этот сертификат не содержат.

Бот уже несёт оба нужных сертификата в `certs/` и подключает их в
`ssl_utils.py` — из коробки проблема возникать не должна. Если она
всё же есть:

1. Проверьте, что папка `certs/` со скопирована рядом с `main.py`
   (не только `.py`-файлы).
2. Если это Windows с антивирусом, проверяющим HTTPS-трафик (Kaspersky
   и похожие) — такой антивирус подменяет TLS-сертификат на свой
   собственный, и никакой бандл сертификатов в приложении это не
   обойдёт. Либо отключите проверку защищённых соединений для Python в
   настройках антивируса, либо, только для диагностики, поставьте в
   `.env`: `MAX_SSL_VERIFY=false` (и `IMPULSE_SSL_VERIFY=false` при
   такой же ошибке для impulseCRM). Это отключает проверку подлинности
   сервера — не оставляйте так в бою.

### `impulseCRM ... вернул пустое тело` / `Expecting value: line 1 column 1`

Означает, что запрос ушёл не туда и сервер ответил пустой страницей
вместо JSON — почти всегда это неверный `IMPULSE_API_PATH`. Откройте в
CRM «Настройка API» → «Пример запроса» и сверьте путь между доменом и
названием сущности с тем, что стоит в `.env`.

## 4. Структура проекта

```
main.py                  # точка входа: polling/webhook, сборка диспетчера
settings.py               # вся конфигурация из .env в одном месте
database.py                # SQLite: пользователи, файлы ДЗ, заявки, лог напоминаний
cache.py                   # кеш уроков (окно −30/+60 дней, обновление раз в 5 мин)
scheduler.py                # APScheduler: напоминания, сводки, проверка баланса
impulse_client.py           # клиент impulseCRM + адаптер схемы к «урокам»
impulse_introspect.py       # снятие реальной схемы полей с вашего аккаунта
ssl_utils.py                 # общий SSL-контекст (certifi + сертификат Минцифры)
certs/                        # сертификаты Russian Trusted Root/Sub CA (см. раздел 3)
max_api/
  client.py                 # HTTP-клиент MAX Bot API
  context.py                # обёртки апдейтов (Msg/Callback — как в aiogram)
  keyboards.py               # сборка inline-клавиатур
bot/
  dispatcher.py              # мини-Router/Dispatcher вместо aiogram
  fsm.py                      # in-memory FSM (как aiogram MemoryStorage)
  states.py                    # имена состояний
  formatting.py                 # карточки уроков, сводки, даты — не зависит от платформы
  handlers/
    start.py                    # вход по телефону, меню, выход
    teacher.py                   # расписание, отчёт, закрытие урока, ДЗ, перенос
    parent.py                     # расписание, ДЗ, баланс, перенос
    manager.py                     # рассылка, заявки на перенос, сводка
    common.py                      # общие хелперы (карты имён, получение уроков)
```

## 5. Известные ограничения

* **Long polling не для продакшена** — так говорит сама документация
  MAX. Переключитесь на `MAX_MODE=webhook`, когда будет готов домен
  с доверенным TLS.
* **Уведомление о нажатии inline-кнопки**: официальная документация
  `POST /answers` описывает только обновление текста сообщения; отдельного
  поля для всплывающего уведомления (как `callback.answer(text,
  show_alert=True)` в Telegram) в описании тела запроса не приведено.
  Пока это не подтверждено, короткие уведомления («❌ Доступно только
  преподавателям») отправляются отдельным сообщением, а не всплывающим
  тостом — см. `max_api/context.py`.
* **Reuse токена вложения**: предполагается, что `token` из входящего
  вложения (файл/фото, присланные пользователем) годится для повторной
  отправки тем же способом, что и `token` от `POST /uploads` — так
  показано в примерах официальной JS-библиотеки, но отдельно для
  входящих вложений вендором не подтверждено.
* Только личные диалоги 1-на-1 — бот не рассчитан на групповые чаты/каналы.

# Обновление: воронка новых клиентов и починка расписания/ДЗ/баланса

## Что было сломано и почему

**1. Диспетчер терял все пошаговые диалоги.** Фильтр `F.text` был
объектом без `__call__`, и любой обработчик с этим фильтром падал внутри
диспетчера с `TypeError`. Исключение гасилось общим `except`, поэтому
внешне это выглядело как «бот не отвечает». Не работали: ввод дат в
сводке менеджера, текст рассылки, комментарий к заявке на перенос, текст
ДЗ, ввод периода расписания у преподавателя.

**2. Расписание у родителя всегда пустое.** Учеников занятия бот брал
только из сущности `reservation`, а она в вашем аккаунте пуста. Теперь
источников три: `reservation`, абонементы с привязкой к группе
(`*_account.groups`) и прямая ссылка `schedule.client`.
**Что нужно сделать в CRM:** привязать абонементы к группам — иначе
связать родителя с его занятиями по-прежнему нечем. Бот пишет об этом
предупреждение в лог при каждом обновлении кеша.

**3. ДЗ у родителя всегда пустое.** Две причины. Во-первых, запрос шёл с
фильтром «только проведённые», а impulseCRM статус занятия не хранит —
условие не выполнялось никогда. Во-вторых, у `schedule` нет полей темы и
домашнего задания вообще, и запись в CRM молча терялась.
Теперь тема, ДЗ и отметка «проведён» хранятся в БД бота (таблица
`lesson_notes`) и накладываются на занятия в одной точке
(`common.apply_lesson_notes`) — их одинаково видят родитель,
преподаватель, сводка менеджера и напоминания.

**4. Баланс всегда нулевой.** Показывались деньги (`client.deposit`,
в этой CRM не используется) и разность «оплачено минус проведено», причём
карта балансов читалась по числовому ключу, а id из CRM приходит строкой —
поиск промахивался. Читалась только одна сущность абонемента из четырёх,
без учёта того, действует он или сгорел.

**5. Синтетические id занятий ломали половину действий.** У повторяющихся
занятий id имеет вид `116:2026-09-01`. Код делал `int(id)` и
`callback.data.split(":")[1]` — падал с `ValueError` либо отмечал не ту
дату. Все id занятий теперь строки, парсинг через `partition`.

## Баланс = остаток занятий

Считается по полю `trainingsLeft`, которое CRM ведёт сама, а не как
`trainingsTotal - trainingsUsed`: при заморозке, продлении и подарочных
занятиях арифметика врёт, а `trainingsLeft` — нет. Учитываются все
действующие абонементы клиента (не закрытые, не архивные, `active`).
Родитель видит суммарный остаток и разбивку по каждому абонементу со
сроком действия.

# Почему расписание и ДЗ всё ещё пустые

Разворачивание расписания работает: `day=2` — это вторник, и `dateBegin`
в вашем аккаунте тоже приходится на вторник, время 16:00–17:00. Занятия
бот строит правильно. Пустыми остаются **ученики на этих занятиях**.

В снятой схеме у абонемента (`group_account` #169, «Абонемент
импортирован») поле `groups` пустое: `[]`. То есть в CRM не записано,
к какой группе относится этот абонемент. А больше связать ученика с
занятием нечем — `reservation` тоже пуста.

Это не ошибка кода: занятия есть, ученики есть, а что кого с чем
связывает — в базе не указано. Пока этого нет, показать родителю его
занятия невозможно в принципе.

## Что сделано, чтобы это не зависело от угадывания

Связь больше не ищется в одном поле с известным именем. Теперь бот
рекурсивно обходит запись и находит вложенные объекты вида
`{"id": 27, "entity": "group"}` — как бы поле ни называлось (`groups`,
`packets`, `clientSubscription` или иное). Источники перебираются все:
`reservation`, абонементы всех четырёх типов, разовые занятия
(`*_single`) и прямая ссылка `schedule.client`. Служебные ветки
(`creator`, `updater`, `branch`) исключены, иначе группа из карточки
создателя записи выглядела бы как связь ученика.

При старте бот пишет в лог, сколько связей нашёл и в какой сущности.
Если связей нет — предупреждает об этом прямо, а не молчит.

## Зонд: `impulse_probe.py`

Выгружает записи целиком (а не по одной, как `impulse_introspect.py` —
именно поэтому пустой `groups` у единственной записи и был принят за
общее правило) и отвечает на три вопроса:

1. какие группы в какое время занимаются;
2. есть ли хоть одна запись, связывающая ученика с группой или занятием,
   и в каком именно поле она лежит;
3. для конкретного телефона — что именно увидит этот родитель.

```powershell
python impulse_probe.py
python impulse_probe.py --phone +79035768618
python impulse_probe.py --dump probe.json
```

Раздел 3 показывает сквозную картину: найден ли клиент, какие у него
абонементы, какой остаток покажет бот и какие занятия попадут в
расписание. Если занятий ноль — там же написано, почему.

## Что нужно сделать в CRM

Достаточно проверить на одном ученике:

- **вариант А** — открыть его абонемент и указать в нём группу;
- **вариант Б** — записать его на занятие (появится `reservation`).

После этого запустить зонд ещё раз: в разделе 2 должна появиться
отметка ✅, а в разделе 3 — список занятий. Тогда и в боте они появятся
(кеш обновляется раз в 5 минут, или перезапустите бота).

# Ученик видел все занятия группы, а ходит не на все

Связь нашлась, но оказалась грубой. Источники были неравноценны, а
складывались как равные:

* **точные** — запись ученика на занятие (`reservation`, разовые
  посещения, `schedule.client`). Здесь сказано именно то, на что ученик
  записан;
* **грубый** — членство в группе через абонемент. Он говорит лишь
  «ученик относится к этой группе», а у группы несколько занятий в
  неделю.

Ребёнок из группы Марины был привязан и к группе, и к конкретным
занятиям. Объединение давало весь график группы.

## Что изменилось

Источники больше не складываются. Если про ученика есть **хоть одна**
точная запись, для него берутся **только** точные — членство в группе к
нему не применяется вовсе. Грубый источник работает лишь для тех, про
кого точных записей нет совсем: такой ученик по-прежнему видит весь
график своей группы, и это правильно — другой информации о нём нет.

То же правило внутри одной записи: если у абонемента есть и ссылка на
занятие, и ссылка на группу, берётся ссылка на занятие.

Состав учеников считается **для каждой даты отдельно**, а не один раз на
правило. Если запись сделана на конкретное число (`reservation` с
датой), остальные даты того же еженедельного правила ученику не
показываются.

Поведение отключается: `STRICT_ENROLLMENT=false` в `.env` вернёт
сложение источников, то есть весь график группы.

## Как проверить

```powershell
python impulse_probe.py --phone +7XXXXXXXXXX
```

Зонд теперь показывает раздельно: какие у ученика точные записи и из
какой они записи CRM, какое членство в группах, что в итоге попадёт в
расписание и — отдельным списком — **что скрыто**: занятия его группы,
на которые он не записан.

Если в скрытых окажется занятие, на которое ребёнок реально ходит —
значит в CRM не хватает записи, и добавить её нужно там. Бот показывает
то, что записано.

# Направление выбирается для каждого ребёнка отдельно

Раньше кнопки были объединением направлений по всем названным
возрастам: родитель двоих детей мог выбрать ровно одно направление, и в
заявке не было видно, кому из детей оно предназначено.

Теперь дети проходят по очереди:

    возраст: «5 8»
      → «Ребёнок 1 из 2» — кнопки для 5 лет  → выбор
      → «Ребёнок 2 из 2» — кнопки для 8 лет  → выбор
      → сводка выбранного → телефон → заявка

Для одного ребёнка ничего не изменилось: ни счётчика, ни сводки —
сразу кнопки, как и было.

В заявке направление хранится вместе с возрастом того ребёнка, которому
выбрано:

    Возраст:     5, 8
    Направление: 5 лет — ♟️ Шахматы; 8 лет — 💻 Программирование

Ребёнок, чей возраст вне рамок школы, не обрывает сценарий: для него
проставляется «Уточнить у менеджера», и опрос идёт дальше по остальным
детям.

Заодно `parse_ages` перестал убирать повторы — «5 5» это двойняшки, и
направления им нужно выбирать по отдельности. Число детей в одной
заявке ограничено шестью: больше — почти наверняка прислали не
возрасты. Ограничение задаётся `MAX_CHILDREN` в `bot/directions.py`.

# Что сохраняется, телефон и уведомления менеджеру

## Что сохранялось при выборе направления: ничего

Это была настоящая дыра. До момента, когда посетитель присылал номер, всё
жило только в FSM — то есть **в оперативной памяти процесса**. Отсюда две
потери:

* человек выбрал направление и передумал оставлять номер — обращение
  исчезало бесследно, менеджер о нём не узнавал;
* бот перезапустили посреди диалога — то же самое.

Теперь черновик заявки пишется в БД сразу, как только назван возраст, и
дополняется на каждом выборе направления (`status='draft'`). Когда
приходит номер, черновик превращается в заявку — новая строка не
создаётся, иначе одно обращение попало бы к менеджеру дважды.

Незавершённые обращения менеджер видит в разделе «Заявки» отдельным
списком: кто, какое направление, какой возраст, когда. Позвонить по ним
нельзя — телефона нет, — но видеть спрос полезно.

## Телефон без спроса: платформа не даёт

В апдейтах MAX приходят `user_id`, имя и username. Номера там нет —
он передаётся **только** во вложении-контакте, которое человек
отправляет сам, нажав кнопку. Это граница приватности платформы, обойти
её нельзя (в Telegram ровно так же).

Что сделано вместо этого: если бот уже знает номер — из привязки к CRM
или из ранее оставленной заявки — он **не переспрашивает**. Заявка
оформляется сразу, с пометкой «если удобнее другой номер, напишите его».
Спрашивают только тех, чей номер неизвестен, и только один раз.

## Уведомления менеджеру о каждом обращении

Ловятся на уровне диспетчера, поэтому попадает **любое** взаимодействие,
включая те, на которые нет обработчика. В каждом уведомлении: кто,
телефон (из привязки к CRM, из прошлой заявки или «не оставлен»), MAX id
и что человек сделал — по смыслу («выбрал направление: Шахматы»), а не
служебным payload.

Отдельным сообщением на каждое действие слать нельзя: один посетитель за
полминуты совершает 5–7 действий, и на десяти посетителях лента стала бы
нечитаемой. Поэтому действия одного человека копятся `MANAGER_NOTIFY_DELAY`
секунд и уходят одной сводкой:

    👤 Активность в боте
    Анна П (нет в CRM)
    📞 Телефон: не оставлен
    🆔 MAX id: 1001

    1. открыл бота
    2. нажал «Я впервые»
    3. написал: 5 8
    4. выбрал направление: ♟️ Шахматы
    5. выбрал направление: 💻 Программирование

Настройки в `.env`:

    MANAGER_NOTIFY_ACTIVITY=true   # выключается целиком
    MANAGER_NOTIFY_DELAY=20        # 0 — слать каждое действие отдельно

Действия самих менеджеров не пересылаются, иначе менеджер получал бы
уведомления о собственных нажатиях. Сбой отправки уведомления не мешает
боту ответить человеку.

# Как узнать MAX id менеджера (ADMIN_MAX_IDS)

Права менеджера выдаются по числовому id из `ADMIN_MAX_IDS`, а до его
заполнения меню менеджера недоступно — получалась замкнутая ситуация.
Теперь есть два способа.

**Способ 1 — команда в боте.** Отправьте боту `/id` (работают также
`/myid` и `/whoami`). Он ответит вашим числом и подскажет, есть ли уже
права. Команда доступна всем: id не секрет, войти по нему нельзя —
он лишь позволяет вам вписать себя в `.env` на сервере.

**Способ 2 — лог при запуске.** Пока `ADMIN_MAX_IDS` пуст, каждое
входящее сообщение пишется в лог:

    🆔 Сообщение от «Владимир К» — MAX id: 555123.
       Впишите его в ADMIN_MAX_IDS в .env, чтобы получить права менеджера.

Как только `ADMIN_MAX_IDS` заполнен, эта строка уходит в DEBUG и лог не
засоряет.

Дальше в `.env`:

    ADMIN_MAX_IDS=555123

Несколько менеджеров — через запятую: `ADMIN_MAX_IDS=555123,555124`.
После правки перезапустите бота.

# «Кнопка не работает»: почему бот молчал

Сами разделы исправны — я прогнал расписание, ДЗ и баланс на подставной
CRM, все три отвечают. Проблема была в том, что при любом сбое бот
не отвечал ВООБЩЕ, и отличить «нет прав» от «упала CRM» от «устаревшая
кнопка» было невозможно. Три источника молчания:

1. **Ошибка внутри обработчика** писалась в лог и на этом всё
   заканчивалось. Человек не получал ничего.
2. **Отказ в доступе** отправлялся всплывающим ответом на кнопку
   (`callback.answer`). В MAX он показывается мельком или не
   показывается совсем.
3. **Кнопка без обработчика** — например, из старого сообщения в
   истории чата, оставшегося от предыдущей версии бота — не давала ни
   ответа, ни даже записи в логе.

Теперь каждый случай виден:

| Ситуация | Что получает человек |
|---|---|
| Не авторизован | «Вы не авторизованы… отправьте /start и войдите по номеру» |
| Вошёл в другой роли | «Раздел только для родителей, а вы вошли как преподаватель» |
| Сбой CRM или ошибка кода | «Не удалось выполнить действие… попробуйте ещё раз» + полный traceback в логе |
| Старая кнопка | «Кнопка из старого сообщения и больше не действует, отправьте /start» |

Сообщения без обработчика тоже логируются — с текстом, состоянием FSM и
id отправителя.

## Что проверить у себя

Нажмите кнопку и посмотрите ответ бота — он теперь называет причину. Если
ответ «вы не авторизованы» или «вошли как преподаватель», дело в роли, а
не в разделе. Если «не удалось выполнить действие» — причина в логе,
пришлите traceback.

И убедитесь, что запущена свежая сборка: при старте в логе должно быть

    📦 Версия сборки: 2026-08-28.8 (диагностика молчащих кнопок)

# Настоящая причина: пустой POST /answers

Разделы «Расписание», «ДЗ» и «Баланс» падали на ПЕРВОЙ строке
обработчика — `await callback.answer()` — ещё до обращения к CRM.

Причина в моём неверном предположении о MAX. Метод `answer_callback`
вызывался с пустым телом: считалось, что нажатие нужно «квитировать»,
иначе MAX сочтёт кнопку необработанной. MAX такой запрос отвергает:

    HTTP 400 на /answers: {"code":"proto.payload",
      "message":"Invalid request. `message` or `notification` required"}

Заодно этот ответ выдал то, чего не было в документации: поле
`notification` существует — это всплывающее уведомление, аналог
`callback.answer(text)` в Telegram.

Что изменилось:

* **Без текста** `callback.answer()` не отправляет ничего. Квитировать
  нечем, а пустой вызов гарантированно даёт 400.
* **С текстом** уходит `notification` — всплывающее уведомление.
  Длиннее 200 символов в него не помещается, поэтому такой текст
  дополнительно досылается обычным сообщением.
* **Сбой квитирования больше не роняет обработчик.** Подтверждение
  нажатия второстепенно: если оно не прошло, человек всё равно получает
  то, ради чего нажимал кнопку.

Проверено на заглушке, которая ведёт себя как настоящий MAX и отвергает
пустое тело: все три раздела отвечают, ни одного вызова `/answers`
впустую.

# HTTP 404 на client/load

Экшен `load` — единственный, работающий по GET (справочник, раздел 4), и
запрос уходил правильно. Но в вашей установке impulseCRM этого метода
просто нет: сервер отдаёт HTML-страницу 404. Исключение всплывало
наружу, а обработчик подставлял его текст в ответ — родитель получал в
чат кусок HTML вместо баланса.

Исправлено с двух сторон.

**Обход `load`.** При 404 (а также 405 и 501) бот запоминает, что
`load` в этом аккаунте недоступен, и берёт запись из общего списка.
Список кешируется, так что повторных полных выгрузок не будет, и
`load` больше не дёргается вовсе. В лог один раз пишется:

    ⚠️ Экшен load недоступен в этом аккаунте (client/load → HTTP 404).
       Переключаюсь на поиск по списку — работать будет, просто чуть медленнее.

Это лечит не только баланс: через `load` читались ещё и занятия.

**Ошибки CRM больше не уезжают родителям.** Техническая подробность
пишется в лог, а человек видит:

    ⚠️ Не удалось получить данные из системы школы.
    Попробуйте ещё раз через несколько минут.
    Если не заработает — напишите менеджеру.

Заодно HTML-простыня в тексте ошибки сворачивается в одну фразу —
«сервер вернул HTML-страницу ошибки вместо JSON, вероятно такого метода
нет по этому пути». В логах преподавателя и менеджера подробности
остались: им они полезны.

Если хотите включить `load` по-настоящему — спросите у поддержки
(@impulsCRM_manager) точный путь для GET-чтения одной записи и поправьте
`IMPULSE_API_PATH`. Но и без него всё работает.
