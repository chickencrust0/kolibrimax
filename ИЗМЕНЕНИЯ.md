# Обновление 2026-09-04.7

    📦 Версия сборки: 2026-09-04.7 (период в расписании родителя, дата в заморозках, лог отметки посещений)

## 1. Выбор периода в расписании родителя

Раньше родителю жёстко показывалась неделя вперёд — посмотреть «что
сегодня» или «что в следующем месяце» было нельзя. Теперь тот же набор,
что у преподавателя: сегодня / завтра / неделя / месяц / свой период.

Payload у кнопок родителя `pschedule:*`, а не `schedule:*`, — иначе
нажатие попадало бы в роутер преподавателя и родитель получал бы отказ
«только для преподавателей». По той же причине заведены отдельные
состояния `ParentDateRangeStates` для ввода своих дат.

Заголовок стал читаемым: «Расписание на 06.09.2026, Вс» или
«Расписание: 06.09.2026, Вс – 13.09.2026, Вс».

## 2. Дата в заморозках

Дата бралась только из поля `lesson_date`, и у части записей оно пустое
— тогда показывался прочерк. Теперь при пустом поле дата достаётся из
самого `lesson_id`: у повторяющихся занятий идентификатор синтетический
и уже содержит дату (`"116:2026-09-08"`). То есть дата всё это время
лежала рядом.

Формат стал человеческим: `08.09.2026 (Вт)` вместо `2026-09-08`.
Применено и у родителя, и в разделе заморозок у менеджера.

## 3. Отметка посещений — усилена диагностика

Сообщение «отметьте занятие через раздел отметки посещений» приходит не
от бота — его возвращает сама CRM. В коде такой строки нет.

Что сделано:

**Отказ больше не проскакивает как успех.** Раньше проверялись только
формы `success=false` и `error`. Если CRM отвечает HTTP 200 с одним лишь
текстовым сообщением — а это как раз ваш случай — бот считал это
успехом. Теперь такой ответ распознаётся как отказ:

    строка с текстом                    -> ОТКАЗ
    {"message": "…отметьте занятие…"}   -> ОТКАЗ
    {"success": false, …}               -> ОТКАЗ
    {"success": true, "message": "ок"}  -> принято

**В лог пишется весь обмен**, а не три идентификатора:

    → check_visits/check: клиент 755, абонемент 153 (groupAccount),
      цель 116 (group), дата 1788566400 (2026-09-08 00:00:00+00:00 UTC)
    ← check_visits/check: {…полный ответ…}

При `LOG_LEVEL=DEBUG` добавляется полное тело запроса. Эндпоинты
`check_visits` вендором не документированы — их форма восстановлена по
фронтенду, поэтому причина отказа всегда в конкретном поле payload, и
без полного тела понять, в каком именно, нельзя.

**Что нужно от вас:** строки `→ check_visits/check` и
`← check_visits/check` из лога после попытки отметки, желательно с
`LOG_LEVEL=DEBUG`. По ответу CRM будет видно, какое поле её не
устраивает, и я поправлю точно, а не наугад.

# Обновление 2026-09-04.6 — счётчик заморозок, причина найдена

    📦 Версия сборки: 2026-09-04.6 (счётчик заморозок: поле определяется по данным, а не только по .env)

## Что показал schema.json

В снятой схеме сущность `client` не выгрузилась (таймаут CRM), но
карточка клиента целиком лежит внутри `deposit.client`:

    phone     list  ["+79370953330"]
    email     null
    address   list  ["16"]        <- 16 заморозок
    lastName  "Наченкова"  name "Алиса"  id 755

Формат — ровно тот, который разбор уже понимал. Проверка на этих
настоящих данных:

    IMPULSE_FIELD_CLIENT_FREEZES=address  ->  16
    IMPULSE_FIELD_CLIENT_FREEZES=email    ->   0

Дело было **не в разборе, а в имени поля**. Счётчик переехал с `email`
на `address`, я прислал обновлённый `.env`, но архив с кодом `.env`
намеренно не перезаписывает — чтобы не затереть ваши ключи. Если на
сервере остался старый файл, там по-прежнему `email`: поле пустое,
и бот честно показывает 0.

## Что исправлено

Код больше не полагается на `.env` в одиночку. `resolve_freezes_field()`
сначала смотрит настроенное поле, и если числа в нём нет — перебирает
кандидаты (`address`, `livingAddress`, …) и берёт то, где число есть.
В лог при этом пишется:

    ⚠️ Счётчик заморозок найден в поле 'address', а настроено 'email'
       (в нём числа нет). Читаю из 'address'.
       Поправьте IMPULSE_FIELD_CLIENT_FREEZES=address в .env.

Проверено: при `.env` = `address`, `email`, пусто или мусор — читается
16. Списание пишет в то же поле, из которого читает (`["16"]` → `["15"]`),
email при этом не трогается.

Рассинхронизация кода и `.env` больше не может сломать счётчик — она
теперь только пишет предупреждение.

## Что сделать на сервере

Не обязательно, но уберёт предупреждение из лога:

    IMPULSE_FIELD_CLIENT_FREEZES=address

# Обновление 2026-09-04.5 — счётчик заморозок, вторая попытка

    📦 Версия сборки: 2026-09-04.5 (заморозки: рекурсивный разбор адреса + freezes_probe)

## Почему прошлая правка не помогла

Я исправил только одну из трёх возможных причин нуля, а снаружи все три
выглядят одинаково — «0 заморозок»:

1. **Клиент не найден.** `load` мог вернуть чужую запись (стояло
   `return items[0]` — «раз что-то пришло, значит это оно»), либо не
   найти вовсе. Бот показывал ноль из чужой карточки.
2. **Поля нет в ответе.** Тогда чинить разбор бессмысленно.
3. **Число в неузнанной форме.** Прошлый разбор понимал только строки и
   объекты с ключами `value/address/text/name/title/street`. Если ключ
   называется иначе — ноль.

Теперь каждая причина пишет в лог отдельным сообщением, и по нему видно,
какая ваша.

## Что изменено

**Разбор поля стал рекурсивным.** Обходятся все уровни вложенности,
берутся любые строковые значения — угадывать имя ключа больше не нужно.
Служебные ключи (`id`, `house`, `zip`, `flat`, `branch`, координаты и
т.п.) пропускаются: число в них означает не заморозки, а номер дома или
идентификатор.

Проверено на всех формах:

| В CRM | Прочитано |
|---|---|
| `["3"]` | 3 |
| `["г. Волгоград, ул. Ленина, д. 5", "2"]` | 2 |
| `[{"value": "ул. Мира, 7"}, "4"]` | 4 |
| `[{"addressLine": "5"}]` — неизвестный ключ | 5 |
| `[{"id": 9, "line": "2"}]` — id не путается с числом | 2 |
| `{"items": [{"text": "6"}]}` — вложенность | 6 |
| `[3]`, `"5"` | 3, 5 |
| `[{"id": 9, "house": "7", "street": "Ленина"}]` | 0 + предупреждение |

**`load` больше не подсовывает чужую запись.** Если ни один id не
совпал, пишется предупреждение со списком пришедших id и запись ищется в
общем списке.

**Клиент не найден — теперь ошибка, а не ноль.** Родитель увидит
«не удалось получить из CRM», а не выдуманное «0 заморозок».

**Нет поля в записи — предупреждение** со списком всех полей, которые
CRM реально отдала.

## Новый скрипт: freezes_probe.py

Только чтение, ничего не меняет. Показывает, что реально лежит в
карточке клиента, и какая из трёх причин ваша.

```
python freezes_probe.py                      # первые 5 клиентов
python freezes_probe.py --id 754             # конкретный клиент
python freezes_probe.py --phone +79001234567
python freezes_probe.py --all                # все с заполненным адресом
```

Печатает список всех полей записи, сырое значение поля адреса, его тип и
то, что из него прочитал бот. Если поле есть, а число не нашлось —
выводит структуру целиком.

# Обновление 2026-09-04.4 — счётчик заморозок

    📦 Версия сборки: 2026-09-04.4 (address как массив — счётчик заморозок читается)

## Причина найдена в документации API

В интерактивной документации impulseCRM, сущность `client`:

| Имя | Тип | Описание |
|---|---|---|
| `email` | string | Электронная почта |
| **`address`** | **array** | **Массив адресов** |

Поле адреса — **массив**, а не строка. Мой код читал его через
`str(raw)`, поэтому значение `["3"]` превращалось в строку `"['3']"`,
которая числом не распознавалась, и бот честно показывал 0.

## Что исправлено

**Чтение.** Массив разбирается поэлементно, число ищется как отдельный
элемент. Значением считается только элемент целиком из цифр — выбирать
цифры из строки нельзя, иначе «ул. Ленина, д. 5» дала бы пять заморозок.

Поддержаны все формы, которые может вернуть CRM:

| В CRM | Прочитано |
|---|---|
| `["3"]` | 3 |
| `["г. Волгоград, ул. Ленина, д. 5", "2"]` | 2 |
| `[{"value": "ул. Мира, 7"}, "4"]` | 4 |
| `[3]` | 3 |
| `"5"` (строка, старый формат) | 5 |
| `["ул. Ленина, д. 5"]` | 0 + предупреждение в лог |

**Запись.** Форма поля сохраняется: в массив пишется массив. Заменяется
ровно один элемент — числовой; настоящий адрес, если он лежит рядом в
том же массиве, остаётся нетронутым. Если числового элемента не было, он
дописывается.

    ["г. Волгоград, ул. Ленина, д. 5", "2"]  ->  ["г. Волгоград, ул. Ленина, д. 5", "1"]

Раньше туда уходила строка вместо массива — CRM либо отклонила бы
запись, либо испортила поле.

## .env

`IMPULSE_FIELD_CLIENT_FREEZES=address` — теперь задано явно,
автоопределение больше не нужно: имя поля подтверждено документацией.

# Обновление 2026-09-04.2 (предыдущее)

Проверить в логе при старте:

    📦 Версия сборки: 2026-09-04.2 (заморозка 5ч + сгоревшие занятия + счётчик в адресе + журнал активности)

## 1. Заморозка — только за 5 часов до занятия

Заморозить занятие (и уважительно, и беспричинно) можно, пока до начала
осталось не меньше `FREEZE_DEADLINE_HOURS` часов.

* В расписании кнопки заморозки прикрепляются только к тем занятиям,
  которые ещё можно заморозить. К остальным — строка «Заморозка
  недоступна: до начала меньше 5 часов».
* Проверка повторяется при нажатии любой кнопки заморозки. Это не
  дублирование: сообщение с кнопкой живёт в истории чата сколько угодно
  долго, и без второй проверки по старой кнопке можно было бы заморозить
  задним числом. Отказ мягкий, с крайним сроком и кнопкой связи с
  менеджером.
* Занятие, у которого не удалось распознать дату/время, НЕ блокируется:
  лучше пропустить заморозку к менеджеру, чем отказать из-за кривой
  записи в CRM.

Файлы: `bot/formatting.py` (`can_freeze`, `freeze_deadline`,
`freeze_deadline_hint`), `bot/handlers/parent.py`, `settings.py`.

## 2. Уведомление о сгоревшем занятии

Задание `scheduler.notify_burned_lessons` (раз в 15 минут). Занятие
считается сгоревшим, когда сошлись три условия:

1. преподаватель отметил ученика как не пришедшего;
2. с начала занятия прошло не меньше `BURN_NOTIFY_AFTER_MINUTES` минут
   (запас на то, чтобы отметку успели поставить);
3. родитель не заморозил это занятие.

Неявки со статусом `excused` пропускаются — там занятие как раз не
сгорело. То же сообщение уходит при ручном списании менеджером
(`manager._notify_parent_burned`); ключ дедупликации общий, двух
сообщений не будет.

Текст: «Занятие сгорело… заморозить уже не получилось… если это ошибка
или была уважительная причина — напишите менеджеру, он разберётся и
вернёт занятие. Ничего страшного не произошло».

**Сознательное ограничение:** уведомление уходит только по детям,
которых преподаватель явно отметил «не пришёл». Если преподаватель забыл
отметить — уведомления не будет, ребёнок попадёт в вечернюю сводку
менеджеру в разделе «никак не отмечены». Сообщать «занятие сгорело» на
основании отсутствия отметки означало бы регулярно врать родителям
из-за забывчивости преподавателя.

Файлы: `scheduler.py`, `bot/handlers/manager.py`, `database.py`
(`get_freeze_for_lesson`).

## 3. Преподавателю не нужна отметка «занятие проведено»

* Кнопка «✅ Отметить как проведённый» убрана из
  `max_api/keyboards.py`. Осталась только посещаемость конкретных детей
  плюс ДЗ и заявка на перенос.
* Обработчик `close:` оставлен, но теперь отвечает «отмечать проведение
  больше не нужно»: сообщения со старыми кнопками живут в истории чата
  сколько угодно долго, и без обработчика нажатие уходило бы в пустоту.
* Отчёт преподавателя перестроен: вместо «Проведено / Не закрыто» —
  всего занятий, отменено, отмечено неявок, с ДЗ / без ДЗ.

Файлы: `max_api/keyboards.py`, `bot/handlers/teacher.py`, `scheduler.py`.

## 4. Счётчик заморозок — в поле адреса проживания

Раньше счётчик жил в `email`, где он конфликтовал с настоящей почтой.
Теперь — в поле адреса.

**Важно:** значением считается только строка ЦЕЛИКОМ из цифр. Выбирать
цифры из строки, как делалось для email, здесь нельзя: адрес обычно
заполнен по-настоящему, и «ул. Ленина, д. 5» дало бы клиенту пять
заморозок. Непустой нечисловой адрес → 0 заморозок и предупреждение в
лог.

Точное имя поля impulseCRM не публикует, поэтому оно определяется по
карточке клиента из списка кандидатов и один раз пишется в лог:

    🏠 Счётчик беспричинных заморозок хранится в поле 'address' карточки клиента

Проверьте эту строку при первом запуске. Если поле не то — задайте
`IMPULSE_FIELD_CLIENT_FREEZES` в `.env`, поиск отключится.

Файлы: `impulse_client.py`, `settings.py`.

## 5. Активность больше не приходит менеджеру сообщениями

Раньше каждая серия действий посетителя уходила менеджеру сводкой в чат.
При десятке посетителей лента состояла почти целиком из активности, и в
ней терялось главное — заявки, обращения и решения по неявкам.

Теперь активность пишется в таблицу `activity_log` и показывается только
по кнопке **«👀 Активность в боте»** в меню менеджера: последние
посетители, у каждого — телефон (из привязки к CRM или из заявки), MAX
id, время последнего действия и список действий по порядку.

Из `bot/notifier.py` ушли буферы, таймеры и задача отложенной отправки —
группировать в момент записи больше не нужно, события группируются по
человеку при показе. Интерфейс класса (`track` / `flush_now` /
`shutdown`) сохранён, поэтому диспетчер и `main.py` менять не пришлось.

Действия самих менеджеров в журнал не пишутся (учитываются оба способа
стать менеджером — `.env` и вход по паролю). Журнал чистится ночным
заданием.

`MANAGER_NOTIFY_DELAY` больше не используется — можно удалить из `.env`.

Файлы: `bot/notifier.py`, `bot/handlers/manager.py`, `database.py`,
`max_api/keyboards.py`, `scheduler.py`, `settings.py`.

## Новое в .env (всё опционально, значения по умолчанию рабочие)

FREEZE_DEADLINE_HOURS=5

## Чего нет в архиве

`.env`, папка `certs/` и `max_api/__init__.py` — их в присланном архиве
не было, поэтому они не тронуты. Распаковывайте поверх рабочей копии,
эти файлы останутся вашими.

Миграция БД не нужна: таблица `activity_log` создаётся при старте
(`CREATE TABLE IF NOT EXISTS`).
